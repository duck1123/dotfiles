# nix-csi and the Self-Hosted Binary Cache

## nix-csi flake input is intentionally pinned

`nix-csi` (the CSI driver `applications/*.nix` files use for the "no Dockerfile" pattern — see the main CLAUDE.md) is pinned in `flake.nix` to a specific commit rather than tracking upstream `master`. As of this writing it's still pinned at `7ddae07bf04c9540084d649a9404900d94adc2fd` (2026-02-25).

**Why:** A routine `nix flake update` once pulled in a later `nix-csi` revision that broke `nur build` two ways:

1. Upstream renamed the whole module `nix-csi` → `nixkube` and restructured options (top-level `authorizedKeys`/`cache.storageClassName` moved to `nixkube.pynixd.authorizedKeys`/`nixkube.pynixd.storageClassName`) and services (separate `nix-cache-lb`/`nix-proxy` LoadBalancers merged into one `pynixd-lb`). This part is just a rename with a known replacement (verified working at the time): `nixkube.pynixd = { authorizedKeys = cfg.authorizedKeys; storageClassName = cfg.cache.storageClassName; };` in `applications/nix-csi.nix`, plus patching `pinIp` to match `"pynixd-lb"`.
2. More seriously, that same upstream commit has a genuine bug: its `pkgs/default.nix` for the `pynixd` package does `if builtins.pathExists ../../pynixd then ../../pynixd else fetchTree {...}` — a dev-convenience fallback that assumes a full git checkout with a sibling `pynixd` directory. Consumed as a flake input (not a checkout), the relative path resolves outside the store, which Nix rejects (`'pynixd' is too short to be a valid store path`). This is forced unconditionally during eval via `pkgs.nixkube`'s propagated build inputs, regardless of any local config, and isn't something we can work around from this repo.

**Before running a general `nix flake update` (with or without `nix-csi` in scope), or touching `applications/nix-csi.nix`:** check whether upstream has fixed the `pynixd` path bug — try bumping just `nix-csi` in isolation (`nix flake lock --update-input nix-csi`) and run `nur build`. If it now builds cleanly, the rename fix above can be reapplied and the pin removed. Until then, leave the pin in place; don't let a general flake update silently move this input forward without re-testing.

## The self-hosted Attic cache exists specifically to feed nix-csi

`applications/attic.nix` / `env/dev/attic.nix` deploy a self-hosted [Attic](https://github.com/zhaofengli/attic) Nix binary cache backed by an S3-compatible store (currently **Garage**, `applications/garage.nix` — see below; RustFS was the original backend and is now disabled, see further down) and the shared Postgres. This exists because `nix-csi`'s own bootstrap components (`cache-init-env`, `node-init-env`, `builder-init-env`, `proxy-init-env` — built from the pinned commit above) were never published to any public substituter (`cache.nixos.org`, `nix-csi.cachix.org`), so a cold cluster had nothing to fetch them from.

Public cache name: `nixos`, at `https://attic.home.kronkltd.net/nixos`, public key `nixos:6s8iAyKEnH2z4spigUdDmt1VwiAwrvPA9vQNUd9if1k=`. Wired as a pull-side substituter (no token needed) in dotfiles' `modules/features/nix.nix`; pushing needs an `attic login` with a per-machine token (`kubectl exec -n attic deploy/attic -- atticadm -f /etc/atticd/server.toml make-token ...`).

`nix-csi` itself is wired to use it as a substituter for its own cache/node/builder roles (`applications/nix-csi.nix`, `nixcsiEval` module — `cache.nixConfig.settings`, `node.nixConfig.settings`, `builders.nixConfig.settings`, each rendering into its own separate nix.conf `ConfigMap`). These are list-typed nix.conf settings, so adding to them from multiple modules **appends** rather than replaces upstream defaults.

**If nix-csi crash-loops citing "no substituter that can build it" for any `*-env` path:** build the missing derivation locally with the same construction `kubenix/options.nix` uses (`nixcsi.pkgs.callPackage "${flake.inputs.nix-csi}/environments/<role>" { dinix = nixcsi.inputs.dinix; }`, swapping `<role>` for `cache`/`node`/`builder`/`proxy`), `attic push nixos <out-path>`, then `nur switch` → commit → push → let ArgoCD sync → `kubectl delete pod` the crash-looping pod to force it to pick up the refreshed ConfigMap.

## Garage backs Attic's storage (current, as of 2026-08-31)

`applications/garage.nix` / `env/dev/garage.nix` deploy [Garage](https://garagehq.deuxfleurs.fr/) (`dxflrs/garage`, hand-rolled resources — no published Helm chart repo exists upstream, only one meant to be cloned from Garage's own git repo) as the S3-compatible backend for Attic's `storage`. Attic shares Garage's single auto-created `"default"` bucket rather than a dedicated one — Garage only provisions one bucket on boot, and atticd's own object keys are content-hash-based, so collision risk with other Garage tenants (e.g. `xyops`) is effectively nil. Point at Garage's **ingress** domain (`https://${config.services.garage.ingress.domain}`), not the in-cluster `garage.garage` ClusterIP — atticd generates presigned nar-download URLs against whatever host is configured, and `garage.garage` only resolves from inside the pod network, so external pulls (any LAN host, or any nix-csi bootstrap that isn't itself a cluster pod) would 404 on DNS.

**Region gotcha (fixed 2026-09-05, commit `a5bc0492`):** an `AWS_REGION`/`AWS_DEFAULT_REGION` env var fix turned out to be a no-op. attic-server's `get_nar` (`server/src/api/binary_cache.rs` upstream) hardcodes `prefer_stream=false` for single-chunk NARs, routing those downloads through a presigned S3 URL whose presigning codepath **signs with `us-east-1` unconditionally** — it ignores both `[storage].region` in `server.toml` and any `AWS_REGION` env var, confirmed empirically by comparing the presigned redirect's signature scope before/after the env var change. Since that codepath can't be configured or disabled from Attic's side, the fix is to align Garage's `s3_region` to `"us-east-1"` instead so it accepts what Attic actually sends (`applications/garage.nix`) — not because Garage cares what the region is named, purely to match what attic-server hardcodes. Any other Garage S3 consumer added in the future needs the same region value if it goes through Attic's presigned-URL path (`xyops` was updated to match for consistency, though its Node-based S3 client isn't actually subject to this bug).

## RustFS — the previous backend, now disabled but still configured (not deleted)

Garage replaced RustFS as Attic's storage backend on 2026-08-31 (`applications/rustfs.nix`/`env/dev/rustfs.nix` still exist with `enable = false;`, kept around rather than deleted). `env/dev/nocodb.nix` was migrated to Garage on 2026-09-06 (re-enabled at the same time, see `applications/nocodb.nix`'s `storage.endpoint` doc for why it uses Garage's ingress domain rather than the in-cluster `garage.garage` ClusterIP).

**One remaining loose end, as of this writing:** `env/dev/longhorn.nix`'s `backupTargetCredential` still points at `rustfs-svc.rustfs:9000` using `secrets.rustfs.*` — Longhorn backups have not been migrated to Garage and are presumably non-functional while RustFS is disabled. Check this before relying on a Longhorn backup existing.

The RustFS-specific gotchas below are kept for reference (relevant again if RustFS is ever re-enabled for one of the above, or reused elsewhere) but don't apply to Attic's current setup:

- RustFS (`rustfs`, Deployment, namespace `rustfs`) is alpha-quality (`rustfs:1.0.0-alpha.90` as of writing) and once crash-looped for 9 days without `kubectl get pods -A` surfacing it (only `grep -v Running` does). Known failure signature: repeated restarts within ~800ms each, `[FATAL] Server encountered an error and is shutting down: File access denied` (a generic message, not tied to a specific path). Root cause observed once: the `rustfs-logs` PVC (256Mi, `local-path` — size isn't actually enforced by `local-path-provisioner`) had accumulated far past its configured retention (243 files / 18.7GB against a "keep 30" policy) — an alpha-quality bug in the log cleaner's handling of a large backlog, not a genuine authz issue despite the error text. Fix: find the PV's host path (`kubectl get pv <pv-name> -o jsonpath='{.spec.local.path}'`), clear out `/logs` inside it via `kubectl debug node/<node>` as root, restart the pod — these are just RustFS's own server logs, safe to delete wholesale.
- RustFS's Service is named `rustfs-svc`, not `rustfs` (the `rustfs.rustfs:9000` endpoint in `env/dev/nocodb.nix` above is this exact bug, still unfixed).
- RustFS's own Helm chart Ingress template hardcodes its backend to the console Service port for every host given to it — the S3 API port (9000) is never reachable through that chart's own ingress mechanism; a working S3-API ingress needed a hand-rolled second `Ingress` resource (`applications/rustfs.nix`'s `extraResources.ingresses.rustfs-api`).
- RustFS's Helm chart defaults `podSecurityContext` to uid/gid `10001`; when backed by NFS this must match a uid the NAS actually grants write access to — see `services.rustfs.uid` in `applications/rustfs.nix`.

## Other Attic config gotchas (only relevant if touching its config again)

- `atticd`'s config: omitting `[database].url` correctly falls back to `$ATTIC_SERVER_DATABASE_URL`, but the `[database]` table header itself must still be present or startup fails with `missing field \`database\`` before any per-field default applies. Same for `[chunking]`/`[compression]` — no serde defaults, real values are required (upstream's `config-template.toml` has working ones).
- `allowed-hosts` must include every Host header actually used to connect: the public ingress domain, `localhost:<port>` (for `kubectl exec` admin commands against `http://localhost:8080`), and `<svc>.<ns>:<port>` for any in-cluster caller.
- The ingress needs the `cert-manager.io/cluster-issuer` annotation explicitly — without it, cert-manager silently never issues a Certificate and Traefik serves its default self-signed cert instead. Check with `kubectl get certificate -n <ns>`; `curl -k` masks this, so check the real issuer via `openssl s_client ... | openssl x509 -noout -issuer`.
- `atticd` reads `server.toml` once at startup with no configHash-style rollout trigger — changing the ConfigMap alone does nothing until the pod is restarted (`kubectl delete pod -n attic <pod>`).
- ArgoCD `PostSync` hooks (e.g. `postgresql-init-databases`) only fire on an actual sync operation, not a `refresh=hard` annotation alone. If a new database entry doesn't show up, trigger a real sync (or run the equivalent SQL by hand — see the Job's own script for the idempotent pattern) rather than just refreshing.
